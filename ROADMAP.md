# Exeris AI Bridge — Roadmap to 1.0.0 GA

The bridge is the **agent-facing surface** of the Exeris ecosystem: an MCP server that exposes semantic surfaces — `docs:*` (ADR registry, HLA, whitepaper), `lsp:*` (Studio/LSP semantic index), `kernel:*` (read-only kernel introspection via `KernelDiagnostics`), and the authoring surfaces `build:*` and `caps:*` (0.6.0), `sdk:*` (0.7.0) — to AI agents over stdio (and later SSE).

**1.0.0 GA means: the MCP tool surface is stable.** Tool names, input schemas, and output shapes are frozen under semver. Third-party agents and IDE extensions can pin to a `@exeris/ai-bridge@^1` and trust that a 1.x bump will not break their prompts or tool-call wiring.

Founding decision: [ADR-025 — AI Agent Bridge / MCP Server for Ecosystem Introspection](docs/adr/ADR-025-ai-agent-bridge.md), as amended 2026-08-16 ("Two Personas").

This file tracks scope per milestone. Items marked `[ ]` are open; `[x]` shipped.

---

## Who this server is for — two personas

Through 0.4.0 the roadmap served exactly one of these, without ever naming it. The 2026-08-16 ADR-025 amendment names both and makes them co-equal through 1.0.

**P1 — ecosystem contributor.** Works *on* Exeris: kernel, SDK, tooling, platform. Has every sibling repo checked out under `~/exeris-systems/`. Needs the ADR registry, cross-repo routing rules, kernel runtime internals. **Served by `docs:*`, `kernel:*`, and the LSP index pointed at an ecosystem repo.**

**P2 — application developer.** Builds *on* Exeris — a product on top of the SDK + tooling. Has **no** ecosystem checkout: a Maven dependency on `eu.exeris:exeris-sdk-*`, the codegen plugin, and their own `@ExerisDomain` sources. Needs the annotation contract, what codegen will emit, why the build failed, and canonical entity edits. **Served by nothing today.**

The gap is structural, not cosmetic. Three concrete pieces of evidence:

1. **Every planned prompt was a P1 workflow** — the pre-amendment prompt list (`review-three-tier-violations`, `draft-adr`, `route-this-task`, `wall-audit`, now at 0.9.0) contained four contributor workflows and not one entity-authoring workflow.
2. **`loadConfig()` fail-fast makes P2 impossible.** `src/config/env.ts` resolves `EXERIS_DOCS_ROOT ?? ../exeris-docs` through `resolveExistingDir`, which throws when the directory is absent, and derives `ecosystemRoot = dirname(docsRoot)` — from which the default LSP and kernel-CLI launch specs are built as `mvn -f <ecosystemRoot>/…/pom.xml`. On a P2 machine there is no such tree, so **the server does not boot at all**.
3. **The write vocabulary already exists and is P2-shaped.** `MutationOp` (SDK `exeris-sdk-source-model`) has nine variants — `AddField`, `RemoveField`, `RenameField`, `ChangeFieldType`, `AddRelationship`, `RemoveRelationship`, `ChangeRelationshipCardinality`, `AddAction`, `RemoveAction` — with `SourceDigest` / `BaselineTrust` for optimistic concurrency, and `exeris/applyMutation` implements idempotent write-back platform-side. The bridge is forbidden from consuming any of it (2026-06-24 amendment). That investment currently serves Studio only.

**Read-only stays intact.** The bridge performs no write, in any family, through 1.0 — see 0.8.0, which delivers *preview* (a canonical diff the agent applies with its own file tools), not *apply*.

> Goal: the bridge introspects a running kernel through a process-boundary adapter. Read-only. Preserves The Wall by construction. **Cap-blind** — the kernel exposes runtime state only; capability composition is a tooling/platform surface, not a kernel one (ADR-024 2026-06-17 "Validation Stamp Lifecycle" amendment; ADR-025 §"`kernel:*` Is Cap-Blind").

> **Phase 4a (2026-06-25) — adapter bound + live data path verified.** The Node-side adapter (`src/transport/kernel-adapter.ts`) spawns the shipped `exeris-kernel-diagnostics-cli` over NDJSON and the three tools validate each snapshot against its wire shape (`src/tools/kernel/shapes.ts`, mirrored 1:1 from the `eu.exeris.kernel.spi.diagnostics.*` records, `schemaVersion` "1.0"). ## 0.5.0 — zero-checkout mode (the P2 foundation)

> Goal: the bridge boots and serves useful answers on a machine that has **no ecosystem repository checked out** — only a Maven dependency on `eu.exeris:*` and the developer's own sources. Nothing in the P2 track is reachable until this lands, so it goes first.

This is a configuration and packaging milestone, not a tool milestone. No new tool family ships here.

- [x] **ADR-025 amendment "Two Personas" ACCEPTED** — gate on everything below; names P1/P2, authorises the three new families, pins the preview-not-write stance. Merged 2026-08-16 (`2b25b8b`, PR #14)
- [x] **Graceful degradation replaces fail-fast** — a missing `EXERIS_DOCS_ROOT` disables `docs:*` (tools report a structured `family_unavailable` error carrying `reason` + `remedy`) instead of throwing out of `loadConfig()`. Boot succeeds unconditionally — even with *no* family available, since a server that reports why it is dark beats one that will not start. The tool surface is invariant: `tools/list` returns the same 17 definitions either way, which is what makes the 1.0 freeze possible
- [x] **`EXERIS_BRIDGE_MODE=contributor|app|auto`** — `auto` (default) probes for an ecosystem layout and picks; explicit values pin the behaviour. `ecosystemRoot` is now `string | null` rather than load-bearing. Mode is *descriptive*, not a mask: it never switches a family off, so availability keeps exactly one source of truth (did the dependency resolve). Pinning `contributor` only changes a missing root from the expected P2 state into a reported misconfiguration
- [x] **Artifact-resolved launch specs** — a launch ladder per child: `EXERIS_*_COMMAND` → `EXERIS_*_JAR` → local-Maven-repo probe by coordinate (no network) → `mvn -f <src>/pom.xml`, only when the module pom is actually there → family unavailable. **Rung order depends on the mode**, and this is the one place mode changes behaviour rather than describing it: contributor puts the source tree first (someone with the checkout is working *on* that tree; a released jar would answer for code they are not editing, and nothing in the answer would say so), app puts the published jar first. Preference, not gating — the second rung still fires when the first cannot. The CLI version comes from the newest **release** of `exeris-kernel-core` present in the local repository — *not* from the project's dependency graph, which would need a Maven invocation and therefore a network round-trip on the boot path; those normally agree, and `EXERIS_KERNEL_VERSION` pins it when they do not. **The ladder passes `--enable-preview` to neither child**, which corrects an earlier claim in this file. `exeris-kernel` went preview-clean **at 0.11.0** (ADR-066, quoted in its own pom: "the DISTRIBUTED artifact is preview-clean"; preview is now bound to test-compile and surefire only), and scanning the published shaded jars puts the boundary exactly there — `0.10.2` carries **12 preview-stamped classes out of 799**, `0.11.0` carries **0 out of 897**. `exeris-platform` uses no preview at all. A pre-0.11.0 kernel jar is therefore out of scope for the jar rungs, deliberately: version-conditional flags would encode upstream release history in the resolver, and the failure is already self-describing (`UnsupportedClassVersionError: Preview features are not enabled … Try running with '--enable-preview'`), which the transport surfaces verbatim. `EXERIS_KERNEL_COMMAND` takes a full command line for exactly this case. **Kernel side is already artifact-launchable** (shaded, `Main-Class` in the manifest, deployed by the root-reactor `mvn deploy`); the LSP side is the remaining **cross-repo dependency** — its published jar carries no `Main-Class` (verified 2026-08-26), so `lsp:*` has no local-repository rung until the companion ask lands — see the asks table
- [x] **Bundled reference data** — the P2-relevant read-only corpus (annotation catalog, AST schema, curated authoring guides) ships *inside* the npm package, generated at release time from released upstream artifacts. No network, no checkout. Establishes the mechanism 0.7.0 fills with content. **Ships with zero entries**, deliberately: the manifest, the loader, the integrity check and the packaging are all real, and putting placeholder content in a public package to prove a pipeline works would be shipping fiction. `data/` is generated by `prepack` and **not committed**, which keeps a stale `generatedAt` out of git and makes the bundle-absent branch the ordinary source-checkout experience rather than one only a test reaches. Every entry carries a SHA-256 verified on read (a truncated file parses fine and is quietly wrong) and a per-entry `sourceArtifact`, so an answer can name which upstream release it reflects; `bridge-version` reports the bundle state, entry count and those artifacts
- [x] **`bridge-health` + `bridge-version`** — **pulled forward from the old 0.7.0.** Zero-checkout resolution has many more failure modes than the ecosystem layout did ("which mode am I in, which families are live, why is `sdk:*` dark"); shipping the diagnostic surface *after* the thing it diagnoses is backwards. Authorised by the ADR-025 2026-08-26 addendum and frozen at two tools. **Zero spawns:** both read boot-time config plus non-spawning `status()` accessors on the two transports. The planned `probe` flag was dropped — the families' own tools already answer "can this child launch?" by doing the work, and the resulting transport state shows up in the next `bridge-health`
- [x] **P2 smoke test** — CI job (`p2-smoke`, `scripts/p2-smoke.mjs`, `npm run smoke:p2`) that packs the real tarball, installs it into a scratch directory containing *only* a minimal Maven project with one `@ExerisDomain` source, points `HOME` at an empty directory, builds the child environment **from nothing** rather than filtering `EXERIS_*` out of the parent (a deny-list fails open the first time a variable is added), and then speaks newline-delimited JSON-RPC to the installed `bin` with a hand-rolled client — the MCP SDK client would swallow exactly the failure worth catching, a server writing something other than a message to stdout. It asserts the boot summary, `mode=app` inferred rather than pinned, all three environment-dependent families dark with a `reason` and a `remedy` that leak no machine path, `family_unavailable` returned **on the wire** for one tool per family, and the bundle live with zero entries — which is what proves `prepack` and `files` carried `data/` into the tarball. Two further guards: `tools/list` is compared byte-for-byte across two processes from the same install, one fully dark and one with `kernel:*` lit by `EXERIS_KERNEL_COMMAND`, so the surface-invariance claim is held where a client would actually observe it breaking; and `assertZeroCheckout` states the negative facts directly, because this test can go vacuous in silence — if the install-neighbour docs default ever resolved, every assertion after it would keep passing while testing nothing

> **0.5.0 closed (2026-08-26).** The package version jumps `0.2.0` → `0.5.0` here: 0.3.0 and 0.4.0 closed as milestones but were never published, so there is no intermediate release for a consumer to have pinned and nothing to bridge. Everything in this milestone is verified against the built package rather than the source tree — that is what the P2 smoke job is for.
>
> Two upstream dependencies stay open, and 0.5.0 ships around them rather than waiting: `exeris-platform-lsp` still publishes no runnable jar, so `lsp:*` has no local-repository rung and remains contributor-only; and the published `exeris-kernel-diagnostics-cli:0.11.0` jar resolves correctly through the ladder but fails to boot on a Jackson 2/3 clash. Both are visible to an agent as a structured transport error rather than a silent dead end, and both are tracked in the cross-repo asks table below.
>
> **Update (2026-08-27).** The kernel half is **fixed upstream and waiting on a release**: the fix is merged into the `0.12.0` development line, so it arrives with kernel 0.12.0 and needs no change here. Nothing moved on the platform half. `exeris-sdk` cut **v0.11.0** — which does *not* advance 0.6.0, because the released artifacts still carry no machine-readable catalog (see the asks table).

## 0.5.1 — the surface a client can actually reach

> Goal: fix a naming choice that made the whole surface unreachable in some clients, and spend the two additions that needed no upstream anything.

- [x] **Tool names are `family-tool`, not `family:tool`** — MCP clients do not reliably resolve a `:` inside a tool name, and the failure is silent: the server registers, `tools/list` looks right, every call misses. The family prefix keeps its job; it is now one family, one hyphen, then `snake_case`, pinned by a test over the whole surface rather than by four per-family prefix assertions that a colon can slip past. `scripts/p2-smoke.mjs` moved with it — it holds the surface across two real processes and was still asserting the old form, which is how this could have shipped green. `family:*` stays the prose spelling for a family in the docs and in ADR-025; agent-facing runtime strings use the wire form, because the agent's only handle on a family is what it can see in `tools/list`
- [x] **Server `instructions`** — MCP delivers them in the `initialize` response, so they reach the model *before* it calls anything. That timing is the whole point: an agent trained overwhelmingly on Spring will design a Spring application here, and a tool cannot correct that, because the agent has to already suspect it needs one to call it — by which point the shape is usually chosen. Deliberately a **route, not a cheat sheet**: what this server is, that every tool is a read, which family answers what, the family states resolved this session, and the one correction (no Spring context, no DI container, no JPA or Hibernate anywhere in the kernel, SDK or tooling — verified, not asserted). Framework facts stay in the documents the tools serve; copied here they would be a second unversioned copy that drifts and that nothing tests
- [x] **`kernel-get_jvm_ergonomics`** — the fourth and last `KernelDiagnostics` method, and the only one the bridge had left unexposed. Answers what the JVM actually *resolved* — selected GC, max/committed heap, visible processors, cgroup CPU quota/period, memory cap, cpuset, large pages, CDS, AOT cache — which is the question behind most "it is slow" and "it got OOM-killed in the container" reports, and one an agent otherwise guesses at from flags that may not have won. Read-only and cap-blind like the rest; it adds no capability to the family. It is a `default` SPI method, so a kernel with no implementation answers `unknown()` — `gcName: "unknown"`, `-1` byte counts — which the shape treats as a valid answer rather than an error. Present in the released **v0.11.0** CLI, so this is not speculative; via the `m2` rung it still waits for kernel 0.12.0 like the rest of `kernel:*`

> **Not published to npm (decided 2026-09-02).** 0.5.1 is tagged work, not a release: publication waits on `exeris-kernel` 0.12.0, `exeris-sdk` 0.12.0 and `exeris-tooling` 0.9.0 reaching **Maven Central**. The reason is the audience. Until those land, every `eu.exeris:*` coordinate the launch ladder probes for resolves only from GitHub Packages, which needs a `PACKAGES_READ_TOKEN`; publishing to npm first would put the bridge in front of P2 developers and then fail at the `m2` rung for a credential reason none of them should have to learn about. The bridge is usable from a source checkout in the meantime, which is the P1 path and does not need the release.

## 0.6.0 — `build:*` and `caps:*` families (the pipeline, from the app's side)

> Goal: the agent can answer "what will this build produce, and why did it fail" about **the user's own project** — the question P2 asks all day and that no current family touches.
>
> **Reordered 2026-09-02: this milestone and `sdk:*` swapped places.** `sdk:*` held 0.6.0 because it is the more fundamental contract, but it had no content source and could not start; this one has had a shipped producer in `exeris-tooling` all along. Ordering by dependency-readiness rather than by conceptual depth costs nothing — the two families do not depend on each other — and it stops the roadmap from parking at a milestone that upstream, not this repo, has to unblock. `sdk:*` follows at 0.7.0, where its own gate is now lifted.

`build:*` is filesystem-bound and reads the user's project, so it inherits the `docs:*` path-sandbox discipline: a pinned project root, never an agent-supplied absolute path.

- [x] **Slice 6a — the project root, and the whole `caps:*` family.** `EXERIS_PROJECT_ROOT` pins the tree; with nothing set the bridge walks up from its working directory to the nearest `pom.xml`, which is what makes it work when an agent starts the server inside a module subdirectory and, in a multi-module build, lands on the module whose own `target/` holds the artefacts. An explicit root is taken as given and is *not* required to carry a pom — naming it is how an operator escapes our guessing. One resolution gates both families, so `build:*` and `caps:*` are always dark together, and both are named anyway wherever the vocabulary is agent-facing. Verified upstream paths, not assumed: `cap-manifest.json` at `src/main/generated/java/` (`GenerateMojo` default), `CapabilityGraph.SCHEMA_VERSION = 2`, and the shape mirrored from `eu.exeris.sdk.composition.CapManifest`

- [x] **`build-get_domain_metadata`** — the processor-emitted `exeris-metadata/<entity>.json` for one entity of the user's project. **Validated at the envelope, not through the AST**, and that is a decision rather than a shortcut: `DomainMetadata` has 40+ components before its nested lists and `@JsonInclude(NON_NULL)` makes an absent key normal, so a hand-written TypeScript mirror would be a second implementation of the SDK's contract, mostly encoding guesses about optionality. What is checked is what the bridge depends on and what ADR-042 pins — `schemaVersion` always, `sourceDigest` when the build could compute one — and the record passes through verbatim. `sdk-get_ast_schema` (0.7.0) vendors `META-INF/exeris/ast-schema.json` and validation deepens then, without the tool surface changing
- [x] **`build-list_domains`** — *added beyond the original list, and needed.* `lsp-list_domains` answers the same question but is contributor-only until the platform publishes an artifact, which leaves P2 — the persona this family exists for — with no way to learn an entity name, so the first `build:*` call would have to be a guess. Also the shape every other family already has: a list beside a get. Decodes the four kinds the processor writes into one flat directory (`enum_`, `capability_`, `view_`, and no prefix for an entity), since the filename is the only thing that records which kind a file is
- [x] **Slice 6b — `build:*` reads the emitted metadata.** Verified against the producer rather than the roadmap prose, which was imprecise in two places: the metadata lands in `target/classes/exeris-metadata` (`CLASS_OUTPUT`, per `ExerisDomainProcessor.METADATA_DIR`), the L1 tree is `src/main/generated/**java**` rather than `src/main/generated/`, and the directory holds **four** kinds of file distinguished only by a filename prefix — `enum_`, `capability_`, `view_`, bare for an entity — which nothing in the roadmap recorded. `entityName` is the Java **simple** name, so that is what the tool takes; agent input is checked against that grammar before it is joined into a path, so a traversal attempt never reaches path resolution and a fat-fingered name gets a sentence about names rather than about sandbox escapes
- [x] **`build-explain_artefacts`** — which files Exeris codegen has generated into this project, each with the generator that produced it and what drove it. Turns "run the build and look" into a question. **Grounded in an observed failure, not a guess:** an agent building on Exeris hand-wrote an `init-db.sql` and got the column naming wrong (`backupStation` where the generator emits `backup_station`) while `exeris-tooling`'s `KernelFlywayGenerator` was already emitting `CREATE TABLE`, indexes, `CHECK` constraints and RLS policies for that entity. Nothing was missing; the generated artefact was simply not discoverable from inside the agent's session, which is exactly the gap this tool closes. **It reads what the pipeline emitted rather than predicting what it would emit** — see slice 6c for why the prose above ("which files the generators *will* produce") was the wrong shape
- [x] **`build-get_detach_state`** — L1 (`src/main/generated/java`, regenerated) vs L2 (detached into `src/main/java/`, owned). An agent that edits a still-generated file loses the edit on the next build; this makes the distinction visible. Ownership is *recorded*, not inferred: `OutputWriter` writes `.exeris-codegen-manifest` at the root of each output tree listing every path that run emitted, and the next run deletes the ones it no longer produces. The detached state rests on weaker evidence by construction — `exeris:detach` destroys the L1 signal on purpose — so the tool reports its observations alongside the verdict
- [x] **Slice 6c — the generated tree: what is in it, and who owns it.** Three roadmap facts corrected against the producer. There are **13** registered per-entity generators, not 12, plus `KernelApplicationGenerator` invoked separately for the project-wide files. `exeris-codegen-ts` exists as a module but **is not wired into the Maven plugin** — `exeris.outputDir` is the one Java root, so `mvn exeris:generate` emits no TypeScript and "plus the TS/Angular emitters" describes no shipped behaviour. And **predicting the artefact set was the wrong design**: only `KernelStreamHandlerGenerator` and `KernelActionStreamHandlerGenerator` state their condition in `supports()`, while the other eleven decide by returning a null sentinel from inside `generate(...)` (on `hasEvents()`, `hasGraphMetadata()`, `isSaga()`, `versioned()`), so a TypeScript prediction would have been a second implementation of eleven internal guards — the trap `caps:*` avoids for the DAG and `build-get_domain_metadata` avoids for the AST. The producer already writes the answer down, so the manifest is the source and the hand-maintained part is only the *explanation* attached to an observed path

- [x] **Slice 6d — `build-explain_diagnostic`.** Decodes a diagnostic the developer pasted, covering the `-Aexeris.strict` "attribute set but no generator consumes it" audit and the deprecated-`@Validation` warn-and-read fallback, and reaching past the processor to the failures a build actually stops on: the `EmptyMetadataException` refusal, detach conflicts, unsatisfied `@Requires`, dependency cycles, the cap-tier Wall, and the missing runtime driver. **Ships with text matching, as forecast** — there is still no code registry upstream, so the ask below stays open as an improvement rather than a blocker. Three things bound the weakness: anchors key on the SDK's own public vocabulary (`@ExerisDomain.tenantScoped`, `DataScope.UNIVERSE`, `@GraphEdge`) rather than on prose, so rewording around them does not break a match; a table of real upstream messages, one per catalogue entry, fails the build the moment an anchor stops finding its own message; and a miss is reported as a gap in the catalogue, never as "not an Exeris problem". Correction to the count recorded below: the processor has **11** `printMessage` sites, not 9, plus five `error(...)` helper call sites that route through one of them
- [x] **`caps-list_capabilities`** + **`caps-describe_composition`** — read `cap-manifest.json` (schema v2) and the `CompositionStamp` (`validated`, `compositionVersion`, `contentBinding`). **This is the family the 2026-06-17 amendment pre-authorised**: it explicitly permits composition introspection sourced from *build-time* artefacts, never from the kernel, and requires "its own ADR-025 amendment" first — which the 2026-08-16 amendment supplies. `kernel:*` stays cap-blind; there is still no `kernel-list_capabilities`
- [x] **Scope discipline** — `caps:*` reads emitted manifests only. It does **not** re-resolve the `@Requires`→`@Provides` DAG; that is `exeris-tooling`'s job and duplicating it here would be a second implementation of a validated contract
- [x] **`caps:*` degrades cleanly on a cap-less project** — still the common case in a *user's own* project, but no longer for want of a producer: the emit → validate → assert pipeline is shipped and covered end-to-end upstream (`exeris-tooling` `CapCompositionE2ETest`, which asserts the manifest pins dependency order rather than alphabetical order). ## 0.7.0 — `sdk:*` family (the authoring contract)

> Goal: an agent writing `@ExerisDomain` code stops guessing. The annotation surface, its canonical scoping rules, and the AST wire format become queryable instead of grep-able.
>
> **Gate lifted (verified 2026-09-02): the content source now exists upstream.** The reason this milestone sat at 0.6.0 and blocked was that nothing published carried a machine-readable catalog, and `@Retention(SOURCE)` ruled out deriving one bridge-side. `exeris-sdk` `main` has since opened the **0.12.0** line and added `exeris-sdk-annotation-catalog` — two annotation processors (`AnnotationCatalogProcessor`, `AstSchemaProcessor`) plus a `JavadocText` reader, wired into `exeris-sdk-annotations` via `annotationProcessorPaths`, emitting `META-INF/exeris/annotation-catalog.json` (`catalogFormat: 1`) and `META-INF/exeris/ast-schema.json` (`schemaFormat: 1`) into the jar. Two consequences for the plan. The **javadoc problem is solved at the only layer that could solve it** — a processor runs while sources are still present, which is exactly what a class file cannot recover. And the artifacts are **jar resources, not release assets**, so the earlier objection ("the GitHub release carries no assets, so there is nothing for `prepack` to vendor") no longer applies: `scripts/vendor-reference-data.mjs` reads the published jar. **This milestone is therefore release-gated, not design-gated** — it needs `exeris-sdk` 0.12.0 published, not a decision here.

The single highest-value item is the **`@Field` vs `@Validation` scoping rule**. It is the most likely place in the whole SDK to introduce a subtle regression (per `exeris-sdk/CLAUDE.md`), it is stated authoritatively in two `package-info.java` files, and today an agent finds it only by reading them. `@Validation.required` is deprecated-for-removal with a processor fallback window — an agent that guesses wrong writes code that compiles with a warning today and breaks at SDK 1.0.0.

- [ ] **`sdk-list_annotations`** — all public `@interface`s across `annotation`, `annotation.system`, `annotation.security`, `annotation.capability` (**51 in the released SDK v0.11.0: 35 root, 10 `system`, 4 `capability`, 2 `security`** — counted from the published jar on 2026-08-27, up from 49 in v0.10.0, and the growth is entirely in the root package), each with `@Target`, `@Retention`, one-line purpose. The drift between two consecutive releases is the argument: a hand-maintained count in this repo is wrong one release later, so **the catalog must be generated upstream**
- [ ] **`sdk-describe_annotation`** — full attribute list per annotation: name, type, default, required-ness, deprecation status + canonical replacement, and the prose rationale from the owning `package-info`
- [ ] **`sdk-get_scoping_rules`** — the `@Field` (shape + lifecycle) vs `@Validation` (constraints) split, `FieldMetadata` as the single AST carrier, and the derived NOT NULL / not-blank semantics, served as structured data rather than as a doc the agent must read and remember
- [ ] **`sdk-list_deprecations`** — everything `@Deprecated(forRemoval = true)` with its replacement and removal version; sourced from the SDK's own `MIGRATION.md` pipeline
- [ ] **`sdk-get_ast_schema`** — JSON Schema for `DomainMetadata` and the ~30 sibling AST records, including the two non-obvious Jackson 3 constraints (`FAIL_ON_NULL_FOR_PRIMITIVES=false`; `@JsonInclude(NON_DEFAULT)` boxed-zero behaviour)
- [ ] **Catalog generation is upstream-owned, not hand-maintained** — the SDK emits the catalog; the bridge vendors it at release. A hand-written catalog in this repo would be stale the first time an annotation attribute changes. **Cross-repo dependency** — see the asks table
- [ ] **Version-skew handling** — the bundled catalog carries the SDK version it was generated from; when the user's project pins a different one, tools say so rather than answering confidently from the wrong contract

## 0.8.0 — mutation preview (canonical edits, still zero writes)

> Goal: when an agent adds a field to an entity, the *canonical* SDK writer decides what the source looks like — not the agent's guess at annotation style. The bridge still never writes.

The mechanism: the agent sends a `MutationOp`, the platform applies it **in-memory** and returns the resulting diff plus a `MutationResult`; the agent writes the file with its own tools. The bridge stays literally read-only, and the idempotent write-back logic stops being Studio-only. Whether the bridge should eventually *apply* directly is deliberately deferred — see Post-1.0 candidates.

- [ ] **`lsp-preview_mutation`** — accepts one of the nine `MutationOp` variants, returns a unified diff + the `MutationResult` outcome, writing nothing to disk. Consumes a **new read-only** `exeris/previewMutation`; **does not** consume `exeris/applyMutation`, per the 2026-06-24 amendment. The op/result vocabulary is already settled upstream by **ADR-042** (`exeris-sdk`, ACCEPTED 2026-06-13), so this tool binds to a settled contract rather than negotiating one. *Settled, not yet frozen* — ADR-042 obligation 3 freezes the constant names and the JSON shape at **its** 1.0.0; the implementation has established them, which is a weaker guarantee and worth not shortening while our own freeze is the live topic. **Cross-repo dependency** — see the asks table
- [ ] **Baseline safety wired through** — the request carries the baseline *and* a concurrency token: `ApplyMutationParams(qualifiedName, op, baselineJson, concurrencyToken)`. The SDK never reads the baseline off disk, so the bridge must send it. Per **ADR-042 obligation 5** the baseline is the last-emitted `exeris-metadata/<entity>.json`, and `sourceDigest` is *one mechanism, not two* — stamped into that file for staleness control **and** passed back as the concurrency token at apply time. `schemaVersion` is stamped but never travels in a request. Drift detection is an **AST-level three-way** comparison (**obligation 4**; the textual-merge alternative was measured and rejected in RFC-2026-06-11, `LexicalPreservingPrinter` leaving an indent-only line behind), so the tool must surface all four `MutationResult` outcomes — `SUCCESS`, `CONFLICT`, `VALIDATION_ERROR`, `NO_BASELINE` (**obligation 3**) — and must not collapse `NO_BASELINE` into a conflict
  - *Two places the implementation diverges from the ADR's own prose, verified upstream 2026-08-26 — build against these, not against the ADR text:* **(a)** the stamping is done by the **annotation processor** (`ExerisDomainProcessor.buildMetadataNode`, behind the javac Compiler Tree API), not by codegen as the ADR says in four places; where that API is absent — some incremental and IDE environments — the digest is skipped and only `schemaVersion` is stamped, degrading rather than failing the build, so `build:*` must treat a digest-less baseline as normal. **(b)** `schemaVersion` is a dedicated `SchemaVersion.CURRENT` constant **decoupled from the Maven artifact version**; ADR-042 left this open and guessed "in practice this is the artifact version", and the implementation took the other branch so a release with no AST change does not read as skew. They agree today (`CURRENT` = `0.11.0` against artifact `0.11.0-SNAPSHOT`) and diverge permanently at that first release
  - *Error-path note:* the ADR maps a digest mismatch to `NO_BASELINE`, but the implementation narrowed that to **apply time** — `checkBaselineTrust` covers only missing / unparseable / schema-skew, because three-way detection by definition runs against source that has already changed. A stale digest is therefore not a detection-time block, and the bridge must not present it as one
- [ ] **Idempotence assertion in the bridge's own tests** — previewing the same op twice against the same baseline returns the same diff; previewing an already-applied op returns an empty diff. This is the bridge-side echo of the platform's idempotent-write-back contract
- [ ] **Explicit non-goal: no raw file writes.** If an implementation ever reaches for `fs.writeFile` against the user's project, it has left this milestone's scope and needs a further amendment

## Versioning policy

- **0.x** — tool surface may change in any release; consumers re-pin per minor bump.
- **1.x** — tool surface stable. Additions are minor bumps. Schema-tightening (narrowing input types, removing optional fields from output) requires a major bump with one minor of deprecation warnings.
- **MCP spec compatibility** — the bridge tracks the latest stable MCP spec. When MCP bumps in a breaking way, the bridge ships a compat shim in a minor; full migration follows in the next major.

Its residual ask is one line — add the module to `exeris-kernel-bom` `dependencyManagement`; at tag `v0.11.0` the BOM manages `spi` / `core` / `community` / `community-kafka` / `community-testkit` / `tck` and not the CLI, so it never arrives transitively even though an app developer does have the kernel in the local repo. *(Publication verified 2026-08-26: `eu.exeris.exeris-kernel-diagnostics-cli:0.11.0` is present in GitHub Packages, so the `continue-on-error: true` deploy step did carry it and `mvn dependency:get` is a real remedy.)* **The platform half is the real ask, and it is larger than a pom edit.** Re-verified 2026-08-27: `exeris-platform` has **no GitHub releases at all**, so there is no release pipeline for a launcher to attach to — the ask is "publish this module", not merely "shade it". What *does* exist on `main` is the read-only protocol slice the bridge binds to (`exeris/domains`, `exeris/domainDescribe`, `exeris/actions` are declared in `ExerisProtocolExtensions`, alongside `LspMain` and 12 source files), so `lsp:*` answers against a source-tree launch and only the artifact rung is missing. Mechanically: `exeris-platform-lsp` carries only `exec-maven-plugin` and produces a thin jar, so it needs a shaded/`jlink`ed launcher with `Main-Class: eu.exeris.platform.lsp.LspMain` — the diagnostics-CLI pom is the pattern to copy (`maven-shade-plugin` with `ManifestResourceTransformer` **and** `ServicesResourceTransformer`; the LSP reaches the source model through `ServiceLoader`). Until that lands, `lsp:*` stays contributor-only. *Also pending upstream (planned 2026-08-26, not yet in the poms): `exeris-platform` comes down from `release 26` to `release 25`, matching the kernel. Until it does, an LSP jar would need JDK 26+ while the kernel CLI needs only 25+ — a floor the bridge cannot paper over, so do not document a single JDK requirement until both agree* |

Every ask is small and well-shaped; none requires a new subsystem. **After the 2026-09-02 reorder there is no blocked milestone on the critical path.** 0.6.0 (`build:*` + `caps:*`) has shipped producers in `exeris-tooling` and can start now; its one soft dependency, stable diagnostic IDs, degrades `build-explain_diagnostic` to substring matching rather than blocking the milestone. 0.7.0 (`sdk:*`) is answered upstream and waits only on the `exeris-sdk` 0.12.0 release. What is left is a queue of **releases**, not of decisions: kernel 0.12.0 lights the `m2` rung for `kernel:*`, sdk 0.12.0 opens 0.7.0. The one ask still genuinely unanswered is the **platform half of 0.5.0 (launchable LSP artifact)**, without which `lsp:*` stays contributor-only — and `exeris-platform` has no release pipeline to attach it to, which makes it both the oldest of the four and the largest.

**Upstream state verified 2026-09-02** — `exeris-kernel` v0.11.0 (dev `0.12.0-SNAPSHOT`, carrying the diagnostics-CLI Jackson fix), `exeris-sdk` v0.11.0 (**dev `0.12.0-SNAPSHOT`, carrying `exeris-sdk-annotation-catalog`** — that line opened since the 2026-08-27 pass), `exeris-tooling` v0.7.0, `exeris-platform` **no releases at all**. Re-verify whenever a row is edited, because every ask here is stated against a moving upstream — and check what a release *contains*, not only that it exists. Both directions of that rule have now bitten: v0.11.0 shipped and moved the catalog ask not at all, and five days later an unreleased development line had answered it in full.

**Cite ADR obligation numbers, not upstream `ROADMAP.md` line numbers.** An ACCEPTED ADR does not move; a sibling repo's roadmap renumbers at every milestone, and a line reference that was right when written silently starts pointing at an unrelated item. Where an implementation has diverged from its own ADR's prose — it happens, and 0.8.0 above records two such cases — cite the obligation *and* say what the code actually does.

## Post-1.0 candidates (explicitly not scheduled)

- **`lsp-apply_mutation`** — direct canonical write-back into the user's project. Deliberately deferred past the preview cut: preview first buys real usage evidence about whether agents want the bridge to own the write at all, or are content to apply a canonical diff with their own file tools. Requires a further ADR-025 amendment redefining the cross-family read-only invariant, and would inherit `SourceDigest` / `BaselineTrust` for concurrency.
- **Project scaffolding** (`app:init`) — generate a new Exeris application skeleton. Overlaps a Maven archetype; decide which surface owns it before building either.
- **Enterprise-private extension** — per ADR-025 §"What is NOT in scope", ships as a separate `exeris-ai-bridge-enterprise` repo, never as a private overlay here.

## Tracking

- Per-milestone follow-ups: open issues with `milestone: 0.X.0` label on `github.com/exeris-systems/exeris-ai-bridge` (repo creation is the first 0.2.0 item).
- ADR amendments: any change to tool family scope, license, or process-boundary contract requires amending ADR-025 (or a successor ADR) before shipping.
- **Cross-repo asks are issued as companion issues in the owning repo**, referencing the milestone here. The 0.3.0 / 0.4.0 rows show the pattern: the bridge-side work lands independently, then binds when the companion ships.
