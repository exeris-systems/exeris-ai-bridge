# ADR-086 — the AI execution layer, bounded to observation before routing (link stub)

**Authoritative copy:** [`exeris-docs/adr/ADR-086-bound-the-ai-execution-layer-to-observation-before-routing.md`](https://github.com/exeris-systems/exeris-docs/blob/main/adr/ADR-086-bound-the-ai-execution-layer-to-observation-before-routing.md)

ADR-086 is a **cross-repo** decision owned by `exeris-docs`. It places the AI execution layer in
`exeris-ai-execution`, holds it to observation before routing, and fixes the direction of every seam
into it: events flow from `exeris-agents` to the layer (§A.2), and this repository sits beside the
layer as a consumer relationship under ADR-025, not inside it (§A.3).

## Why this stub exists

§A.3 binds this repository in one sentence: **`exeris-ai-bridge` is a context adapter to the
execution layer, later, under ADR-025 — never its host.** The bridge's mission runs from Exeris
surfaces *to* agents; the execution layer runs the other way, from agent runs to a dataset. The two
directions do not share a home.

So the bridge does not capture runs, does not hold a dataset, and does not host an oracle. A pull
request that adds any of the three here is out of bounds under §A.3, whatever its size and however
read-only it looks — a handler that records what an agent did, a store of run rows, or a check that
judges a run's outcome all belong in `exeris-ai-execution`.

The adapter role itself is not yet authorised. ADR-086 lists it as out of scope ("under ADR-025,
later, by its own amendment"), so a tool that exposes the execution layer's data to agents waits on
an ADR-025 amendment, the same as any new tool family.

Engineering Protocol 6 of the ADR owes this stub; it is paid here.

## When to consult ADR-086

- A proposal to record, log or persist what an agent did through the bridge.
- A proposal to add a tool family or tool that reads from `exeris-ai-execution`.
- Any change that would make the bridge judge, score or compare agent runs or models.
