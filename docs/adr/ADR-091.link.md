# ADR-091 — exeris-tooling's opt-in application starter (link stub)

**Authoritative copy:** [`exeris-tooling/docs/adr/ADR-091-opt-in-application-starter.md`](https://github.com/exeris-systems/exeris-tooling/blob/main/docs/adr/ADR-091-opt-in-application-starter.md)

ADR-091 is a **cross-repo** decision owned by `exeris-tooling`. From exeris-tooling 0.9.0 on, three
opt-in POM modules give a consumer a correct build for a generated application instead of one written
by hand:

- **`exeris-app-bom`** manages the tooling, kernel and SDK artefacts at the versions that tooling
  release was built and tested against, and the code-generation plugin. Release order is kernel →
  SDK → tooling, so the tooling version names the triple.
- **`exeris-app-parent`** inherits that BOM and wires the build: `release 25`, the processor on
  `annotationProcessorPaths`, `generate`, `verify-capabilities` and `verify-runtime` bound, and a
  `<resource>` for the generated migrations and OpenAPI.
- **`exeris-app-starter`** (packaging `pom`) carries the SDK annotations (`compile`), kernel SPI and
  Core, the Community driver at run time, the composition runtime and Jackson 3. The JDBC driver
  stays the application's.

Amendment 2 sets the consumer's own POM: it states the tooling version once, in `<parent>`, because
the BOM also manages `exeris-app-starter`, and it blanks `url`, `licenses`, `developers` and `scm`,
which it would otherwise inherit from the published parent.

Amendment 1 extends this to three shapes of application: backend, frontend (an npm starter on the
`@exeris/codegen-ts` side), and backend + frontend. The generators emit none of these files.

## Why this stub exists

This repository consumes the decision in `build-get_starter` (ADR-025, 2026-10-04 amendment). What
binds the bridge:

- **Return the build ADR-091 describes, not one of our own.** The tool answers with a `pom.xml` on
  `exeris-app-parent` + `exeris-app-starter`, the `@exeris/codegen-ts` entries for a frontend, or
  both, and names what the application still supplies (the JDBC driver). It never adds a dependency
  the starter does not carry.
- **The POM has Amendment 2's shape.** The tooling version appears once, in `<parent>`, and the
  POM carries the empty `url`, `licenses`, `developers` and `scm` elements, so the application does
  not claim Exeris's project metadata as its own.
- **The version is the tested triple.** The bridge pins the `exeris-app-bom` version it vendored at
  release; it does not combine kernel and SDK versions itself.
- **The three variants are Amendment 1's.** A fourth shape needs an amendment upstream first.

## When to consult ADR-091

- Changing what `build-get_starter` returns, or the version it pins.
- A tooling release that changes the starter modules, their scope, or the variants.
