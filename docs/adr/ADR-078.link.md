# ADR-078 — exeris-tooling's runtime-driver gate (link stub)

**Authoritative copy:** [`exeris-tooling/docs/adr/ADR-078-runtime-driver-gate.md`](https://github.com/exeris-systems/exeris-tooling/blob/main/docs/adr/ADR-078-runtime-driver-gate.md)

ADR-078 is a **cross-repo** decision owned by `exeris-tooling`. The `exeris:verify-runtime` goal,
bound to `process-classes`, fails the build when the generated application has no provider registered
for an SPI it needs. It scans the resolved runtime classpath for `META-INF/services/<spi>`, derives
the required SPIs from what the pipeline emitted rather than from the `subsystems()` string, and its
message names the artefact to add (`eu.exeris:exeris-kernel-community`), not the subsystem.

The generators emit no `pom.xml` or other build file. ADR-091 narrows the premise that tooling does
not own the consumer's build, by publishing opt-in starter modules, and keeps that rule.

## Why this stub exists

This repository consumes the decision in two places:

- **`build-explain_diagnostic`** decodes the `verify-runtime` failure for a missing runtime driver;
  the catalogue entry's fix follows the gate's message and its `-Dexeris.verifyRuntime.skip=true`
  escape for a module that only generates code.
- **`build-get_starter`** (ADR-025, 2026-10-04 amendment) serves the starter build as data the
  bridge holds. Nothing the generators emit is involved, so the rule that they emit no build file
  stands.

## When to consult ADR-078

- Changing the catalogue entry for the missing-driver failure.
- A tooling release that changes the SPIs the gate requires, its message, or its skip property.
- Any change that would have the bridge produce a build file from generator output.
