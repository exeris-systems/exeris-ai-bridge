# ADR-097 — exeris-tooling's generator catalogue and launchable generator (link stub)

**Authoritative copy:** [`exeris-tooling/docs/adr/ADR-097-generator-catalogue-and-launchable-generator.md`](https://github.com/exeris-systems/exeris-tooling/blob/main/docs/adr/ADR-097-generator-catalogue-and-launchable-generator.md)

ADR-097 is a **cross-repo** decision owned by `exeris-tooling`. From exeris-tooling 0.10.0 on, two
things are published for tools that read a generated tree:

- **The generator catalogue**, `META-INF/exeris/generator-catalogue.json` in
  `eu.exeris:exeris-codegen-java` (`catalogueFormat: 1`), with its human table in
  [`exeris-tooling/docs/generators.md`](https://github.com/exeris-systems/exeris-tooling/blob/main/docs/generators.md).
  One row per path shape the Java pipeline writes, for the main and the test output roots, naming the
  generator that writes it. The TypeScript generators are described in the same document; their
  machine-readable rows (`outputRoot: "ts"`) are reserved and not in the JSON yet.
- **The launchable generator**, `eu.exeris:exeris-codegen-cli`, a shaded jar run as
  `java -jar exeris-codegen-cli-<version>.jar --metadata-dir=… --output-dir=…`, with `--base-package`,
  `--tests`, `--test-output-dir`, `--allow-empty` and `--print-catalogue`. Exit code `0` success,
  `1` generation refused or failed, `2` invalid arguments; every non-zero exit prints an `EXT-`
  identifier (ADR-095). JDK 25 or newer.

## Why this stub exists

This repository is the consumer the decision names. `build-explain_artefacts` explains the paths an
`.exeris-codegen-manifest` lists from a producer table kept by hand, and `build-preview_generation`
reports the Java generator unavailable for want of a launchable artefact. What binds the bridge:

- **Match manifest paths only.** Read paths from `.exeris-codegen-manifest`, never from a directory
  listing. Take the first row, in catalogue order, whose `outputRoot` is the manifest's tree and whose
  `pathPattern` matches. Strip a leading `./` first: the TypeScript manifest records its project-root
  scaffold files that way, the Java manifests never do.
- **Never evaluate `condition`.** It is text for a person. Evaluating it would be predicting emission,
  which `build-explain_artefacts` already refuses to do.
- **Resolve or report `ambiguousWith`.** The handler package has three rows whose shapes overlap for
  some entity names (`{E}StreamHandler`, `{E}{Action}StreamHandler`, `{E}Handler`). Separate them with
  the entity names from the metadata directory, or report every candidate.
- **Key on `id`, not on the explanation text.** An id is never reused. A path-shape change retires the
  id, lists it under `retired`, and names its replacement.
- **Ignore unknown keys; refuse an unknown `catalogueFormat`.** The format number changes only when an
  existing key is removed or changes meaning.
- **The jar is a tool.** It is in `exeris-tooling-bom`, not in the application starter. Its output is
  byte-identical to what `exeris:generate` writes from the same metadata and base package.

## When to consult ADR-097

- Changing `build-explain_artefacts` or `build-preview_generation`.
- A tooling release that adds, moves or retires a catalogue row.
- Any change that classifies files in a generated tree.
